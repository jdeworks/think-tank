# Section: Risks & Mitigations

## What to Capture
- For each risk: description, category, impact, likelihood, mitigation strategy
- Categories: technical, resource, timeline, budget, security, other

## Questions to Ask
1. What's the biggest thing that could go wrong with this project?
2. What happens if you can't find users in the first month?
3. Are there any technical unknowns you're worried about?
4. What if a key dependency breaks or gets discontinued?
5. What's your plan if this takes 3x longer than expected?

## Quality Tips
- Every project has at least 3 risks. If you can't find them, you're not looking hard enough.
- The biggest risk is usually not technical — it's "nobody wants this." Validate demand early.
- For each risk, have a concrete mitigation, not just "we'll deal with it."
- Categorize risks: technical (can we build it?), market (do people want it?), resource (do we have the capacity?).
- Revisit risks monthly. New ones emerge, old ones get resolved.

## Common Mistakes
- Only listing technical risks (market and resource risks are usually bigger)
- Vague mitigations ("we'll be careful" is not a plan)
- Not having a "kill switch" — at what point do you stop and reassess?
- Ignoring dependency risks (what if that npm package is abandoned?)
- Not considering the risk of success (what if you go viral and can't handle load?)
